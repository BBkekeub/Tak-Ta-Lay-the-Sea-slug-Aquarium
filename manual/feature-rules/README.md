# หนังสือกฎตรวจฟีเจอร์ใหม่ — ทากทาเล

ฉบับ 1 · 19 กันยายน 2026 · ใช้กับการเพิ่มฟีเจอร์ แก้บั๊ก และปรับประสิทธิภาพ

เป้าหมายคือเพิ่มฟีเจอร์โดยไม่ทำให้เกมเดิมพัง ไม่เพิ่มงานซ้ำโดยไม่จำเป็น และรู้จากหลักฐานว่างานเสร็จจริง เปิดอ่านแบบหน้าเว็บได้ที่ [index.html](index.html)

ทำตู้ที่มีเกมอยู่ข้างใน เช่น แข่งวิ่ง ชักเย่อ กินจุ ปาหิน ต้องผ่านเล่มนี้ก่อน แล้วอ่าน [กฎการทำตู้เกม](contest-tanks.md) ต่อ

## 1. กฎก่อนเริ่มงาน

- อ่าน AGENTS.md และตรวจโค้ดล่าสุด รวมถึง git diff และบันทึกของผู้ทำงานอื่น อย่าสรุปจากแผนเก่าว่างานยังไม่ถูกทำ
- ระบุพฤติกรรมที่ผู้เล่นจะได้รับ พร้อมเหตุการณ์ที่กระตุ้น เช่น “เมื่อพัสดุถึง ปุ่มเปิดใช้งานได้โดย focus ไม่หาย”
- ระบุเจ้าของ state และระบบที่อ่าน/เขียนข้อมูลนั้น ตรวจ hook หรือฟังก์ชันที่ถูกเขียนทับภายหลังด้วย
- ตรวจสิ่งที่มีอยู่ก่อนเพิ่ม cache, timer, renderer, event listener หรือระบบเซฟใหม่ ใช้โครงสร้างเดิมเมื่อเหมาะสม
- ห้ามทับงานที่ไม่เกี่ยวข้อง ห้ามรีเซ็ตไฟล์หรือเซฟผู้ใช้เพื่อให้ทดสอบง่าย ใช้โปรไฟล์และเซฟทดสอบแยก
- เลือกหมวดตรวจจากตารางด้านล่างก่อนลงมือ ถ้าไม่เกี่ยวให้บันทึก “ไม่เกี่ยว” พร้อมเหตุผลสั้น ๆ ไม่ต้องทดสอบทั้งเกมทุกครั้ง

## 3. รายการตรวจขั้นต่ำทุกงาน

- พฤติกรรมหลักตรงตามคำขอ และข้อจำกัด/เงื่อนไขผ่านชัดเจน
- เส้นทางสำเร็จ ยกเลิก ทำซ้ำ และกรณีว่าง/ค่าขอบเขตที่เกี่ยวข้องทำงาน
- ฟีเจอร์ข้างเคียงที่ใช้ state เดียวกันยังทำงาน เช่น ย้ายทากแล้วคลัง ตู้ และจำนวนรวมตรงกัน
- ตรวจ syntax และ error ในเส้นทางที่เปลี่ยน แยกปัญหาเดิมกับปัญหาใหม่ด้วยการทำซ้ำ ไม่เรียกปัญหาว่าเดิมโดยไม่มีหลักฐาน
- ตรวจ diff ว่าไม่มีไฟล์/ข้อมูลลับ/เซฟ/การแก้ที่ไม่เกี่ยวติดมา
- เลือกการตรวจที่พิสูจน์พฤติกรรมจริง ไม่เขียนเทสต์เพียงลอก implementation การแก้ข้อความเล็กน้อยใช้การตรวจด้วยตาได้
- ถ้าเทสต์ต้องพึ่ง CDN ให้แยก dependency โหลดไม่สำเร็จออกจากบั๊กเกม ห้ามถือ timeout เป็นผ่าน

## 4. กฎงานภาพและการควบคุม

- ตรวจทั้ง 4 ทิศที่เกมรองรับ พร้อมใกล้/ไกล แพน ซูม และขนาดจอที่เกี่ยวข้อง ต้องไม่มีชิ้นส่วนหายหรือสัดส่วนผิด
- ตรวจการบังหน้าหลัง กระจก เงา และความโปร่งใส: หน้าตู้ หลังตู้ ในตู้ รวมถึงตอนถือ/ย้ายวัตถุ
- hit test, จุดคลิก และกรอบเลือกต้องตามภาพหลังหมุน/ซูม ไม่ใช่ตามตำแหน่งเก่า
- เปลี่ยนสี ยีน วัสดุ ท่าทาง หรือทิศแล้ว cache ต้อง invalid ถูกจุด เปลี่ยนแค่กล้องต้องไม่สร้าง geometry โลกคงที่ใหม่
- ข้อผิดพลาด shader ต้องมองเห็นและวินิจฉัยได้ ตรวจ attribute/uniform/texture limits ของอุปกรณ์เป้าหมายก่อนเพิ่มข้อมูลต่อ vertex อย่าสมมติว่าทุกเครื่องมีข้อจำกัดเท่ากัน
- ห้ามใช้สีหรือ state ร่วมผิดขอบเขต เช่น uniform เดียวแทนค่าที่ควรต่างกันต่อ instance โดยไม่พิสูจน์ว่าทั้ง batch ใช้ค่าเดียวกันจริง
- ภาพนิ่งให้ reuse ภาพ/geometry เดิม ไม่คำนวณใหม่ทุกเฟรม จอคอมร้านนิ่งจนมีข้อเสนอ เควส หรือออเดอร์เปลี่ยน ขยับเฉพาะตัวแจ้งเตือนที่จำเป็น

หลักฐานที่เหมาะสม: ภาพก่อน–หลังในสภาพเดียวกัน, screenshot สี่ทิศเมื่อเปลี่ยน geometry/transform, ตัวนับ rebuild, hit-test assertion และ shader error log ตามสิ่งที่เปลี่ยน

การเรียก draw ครบสี่ทิศโดยไม่ error ยังไม่เท่ากับตรวจว่าภาพถูกต้อง ต้องระบุให้ตรงว่าทดสอบระดับไหน

## 5. กฎประสิทธิภาพ

- ก่อนเพิ่ม per-frame loop, polygon หรือ allocation ต้องอธิบายประโยชน์ที่เห็นได้ และตรวจต้นทุนในฉากที่เป็นตัวแทน
- คัดวัตถุนอก viewport ก่อนงานภาพแพง ฉากไม่ active/แท็บซ่อนไม่ส่งงานวาดของฉากนั้น แต่ชีวิตเกมยังเดินตามนโยบายเวลา
- แคชต้องระบุ key, เหตุที่ invalid, เพดาน และวิธี release ตรวจ pan/zoom reuse และการเปลี่ยนข้อมูลแล้วภาพไม่ค้าง
- แยกเวลาของ simulation, pose, packing/upload, rendering, UI และ save ตามส่วนที่เปลี่ยน ไม่เหมาว่า polygon เป็นคอขวดเสมอ
- ถ้าอ้างว่าเร็วขึ้น ต้องมี before/after ฉากเดียวกัน จำนวนวัตถุเดียวกัน กล้องและความละเอียดเดียวกัน และแยก cold load ออกจากหลัง warm-up
- รายงาน frame-time p50/p95/p99 หรือ spike ที่เกี่ยวข้อง ไม่ใช้ FPS สูงสุดอย่างเดียว จำนวน call ที่ลดลงพิสูจน์งานซ้ำลดลง แต่ยังไม่พิสูจน์ FPS เพิ่ม
- เริ่มจากฉากปกติที่ผู้เล่นใช้ แล้วเพิ่มโหลดตามความเสี่ยง เครื่องแรง/DevTools throttling ไม่แทนผลบน iGPU หรือเครื่องสเปคต่ำจริง
- ทดสอบแคชเมื่อแพน/ซูมต้องไม่ rebuild ของคงที่ และเมื่อปิด/หลุดจอต้องไม่มีงาน render ของส่วนนั้น ห้ามนับ simulation ที่จำเป็นเป็นงาน render

เป้าหมายตั้งต้นของโหมดต่ำคือ 30 FPS หรือประมาณ 33.3 ms ต่อเฟรมบนเครื่องฐานในคู่มือ แต่ไม่ใช่คำรับรอง การไม่ถึงเป้าต้องรายงานคอขวด/ข้อจำกัดที่วัดได้ ไม่แต่งผลทดสอบ

## 6. กฎเวลา Simulation และการเดิน

- ระบุว่าใช้เวลาจริง เวลาที่เปิดเล่น หรือเวลาจำลอง ห้ามใช้ปนกันโดยไม่มีการแปลง
- ความหิว การโต ผสมพันธุ์ บัฟ หมดเวลาข้อเสนอ และคิวต้องไม่หยุดเพราะเลื่อนกล้องออกหรือเปิดตู้/หน้าแข่ง
- ทดสอบความถี่เรียกต่างกัน เช่น 16, 33, 100 และ 1,000 ms แล้วเทียบเวลาสะสมตามนโยบายเดียวกัน
- ห้าม clamp dt แล้วทิ้งเวลาที่ควรเดิน เฉพาะการเคลื่อนที่อาจแบ่งก้าวเล็ก แต่ timer ต้องรักษา elapsed หรือมีนโยบายชดเชยที่ระบุ
- หลังซ่อนแท็บหรือเครื่องพักต้องไม่ทำ catch-up ทั้งหมดในเฟรมเดียวจนค้าง จำกัดงานต่อรอบและระบุว่าจะเก็บ backlog/ชดเชยอย่างไร
- แยกเจ้าของการอัปเดต: ห้ามหน้าร้านและหน้าตู้เดินวัตถุตัวเดียวกันซ้ำในช่วงเวลาเดียว
- ย้ายของระหว่างเดินต้องยกเลิกเส้นทางล้าสมัย คำขอเส้นทางต้องมีอายุ/priority ป้องกันบางคนไม่ได้รับบริการ
- ทดสอบประตูแคบ เดินสวน ถือของ กลุ่มครอบครัว และหยุด/เปิดร้านตามขอบเขตที่แก้ ไม่แก้ความลื่นจนคนทะลุหรือคิวเสีย

## 7. กฎ UI ปุ่ม และคีย์ลัด

- ข้อมูลคงเดิมต้องไม่สร้าง DOM การ์ดหรือ dialog ทั้งก้อนซ้ำเพียงเพราะ timer เดิน อัปเดตเฉพาะ field ที่เปลี่ยน
- หลัง refresh ต้องรักษา focus, การเลือกข้อความ, scroll และสถานะพับ/ขยาย เมื่อรายการยังเป็นตัวเดิม
- รายการมี id คงที่ การเพิ่ม/ลบต้องไม่ทำให้ปุ่มชี้ข้อมูลผิดตัว ทดสอบข้อมูลถูกย้ายหรือลบระหว่างเปิดหน้า
- ปิด dialog แล้วหยุด rAF/observer/งานวาดของหน้านั้น เปิดซ้ำไม่เพิ่ม listener หรือ loop ซ้อน
- ปุ่มซื้อ/รับรางวัล/เปิดกล่องต้องไม่ทำซ้ำจาก double click หรือ callback ซ้อน disable ปุ่มอย่างเดียวไม่พอ ต้องตรวจ state ตอนลงมือด้วย
- คีย์ลัดต้องไม่แย่งการพิมพ์ใน input/textarea/contenteditable ตรวจ Ctrl/Cmd และ physical key หากรองรับภาษาไทย; Esc ยกเลิกต้องคืน state ถูกต้อง
- ทดสอบจอเล็ก ปุ่มสัมผัส และการเลื่อนเมื่อ UI เปลี่ยน ตรวจ label/สถานะปิดใช้งานให้ผู้เล่นรู้ว่าเกิดอะไรขึ้น
- การกระทำที่ถูกปฏิเสธต้องบอก "เหตุผลที่แก้ได้" ไม่ใช่แค่ว่าทำไม่ได้ หรือไล่เหตุผลที่เป็นไปได้ทั้งหมดมากองรวมกัน และถ้ามีพรีวิว ให้บอกตั้งแต่ตอนพรีวิว ไม่ใช่รอให้กดแล้วค่อยรู้
- hidden UI อาจยังคำนวณเวลาจำเป็น แต่ไม่สร้างภาพหรือเขียน DOM ที่ไม่จำเป็น

## 8. กฎข้อมูล เซฟ และเศรษฐกิจ

- บอกว่าข้อมูลใด persistent และข้อมูลใดเป็น runtime/cache ห้ามเซฟ canvas, geometry, DOM หรือ pointer runtime
- ข้อมูลใหม่ต้องมี default และอ่านเซฟเก่าได้ ถ้า schema เปลี่ยนให้มี migration ที่รันซ้ำได้อย่างปลอดภัย
- ทดสอบ save → reload → ใช้งานต่อ รวม state ที่กำลังทำอยู่ เช่น แข่ง ผสมพันธุ์ ส่งของ และรางวัลที่รับแล้วตามขอบเขตงาน
- เงิน/สิ่งของ/ทาก/รางวัลต้องย้ายหรือเพิ่มครั้งเดียว ตรวจยอดก่อนหลังและ ledger/idempotency ที่ระบบใช้ ไม่พึ่งแค่หน้าจอปุ่ม
- ลบจดหมายหรือปิดหน้าแล้วต้องไม่รับรางวัลซ้ำ เปลี่ยนลำดับเควสต้องไม่แจกของเดิมใหม่
- ตรวจข้อมูลว่าง ค่าผิดชนิด NaN/Infinity และ id ที่อ้างวัตถุที่ถูกลบ การโหลดผิดต้องไม่ทำลายเซฟเดิมเงียบ ๆ
- วัด stringify/sign/write หากเพิ่มขนาดหรือความถี่เซฟ โดยเฉพาะใน timer หรือการแข่งขัน อย่าลดการเซฟโดยไม่ระบุช่วงเสี่ยงข้อมูลหาย
- รักษากลไกความสอดคล้องและ CoinGuard เดิม การเปลี่ยนเป็น async storage ต้องคิดถึงลำดับ write และ transaction
- ทดสอบ storage เขียนไม่ได้ด้วย test double หรือพื้นที่ทดสอบแยก ห้ามทำให้ storage ผู้ใช้เต็มเพื่อทดลอง

## 9. กฎอายุทรัพยากรและไฟล์ใหม่

- ทุก resource ต้องมีเจ้าของและจุดปล่อย: timer, rAF, listener, observer, geometry, material, texture, bitmap, audio และ object URL ตามที่สร้าง
- ของที่แชร์กันต้องไม่ dispose เมื่อผู้ใช้รายหนึ่งเลิกใช้ ให้จัด ownership/ref count หรืออายุระดับฉากให้ชัด
- cache/pool ต้องมีเพดานและรีเซ็ต state ก่อนใช้ซ้ำ ไม่ให้ทากหรือลูกค้าคนใหม่รับเป้าหมาย/รางวัล/ท่าของตัวเก่า
- ทดสอบเข้าออกหน้า/ตู้หรือสร้างลบสิ่งของซ้ำ ดู resource count และ memory trend หลังสงบ ไม่ตัดสิน leak จาก heap ขึ้นชั่วคราวครั้งเดียว
- asset ต้องอยู่ในโปรเจกต์และมี path ที่ใช้ได้บนเครื่องอื่น ตรวจตัวพิมพ์เล็กใหญ่และกรณีโหลดไม่สำเร็จ ห้ามอ้างไฟล์เฉพาะเครื่องโดยไม่ตั้งใจ
- โมเดลใหม่ให้บันทึก triangles, vertices, materials, textures และ bones ที่เกี่ยวข้อง การนับเหลี่ยมต้องระบุรวมผม/ของถือ/variant หรือไม่
- อย่าเพิ่ม dependency หรือ framework เพื่อแก้ปัญหาเล็กโดยไม่พิจารณาต้นทุนโหลดและบำรุงรักษา

## 10. หลักฐานก่อนส่งงาน

สถานะที่ใช้ได้มี “ผ่าน”, “ไม่ผ่าน”, “ยังไม่ได้ตรวจ” และ “ไม่เกี่ยว” ห้ามใช้คำว่า “ผ่าน” กับการเดาจากโค้ดหรือกรณีที่เทสต์ไม่ได้เริ่มเพราะ dependency หาย

- สรุปว่าพฤติกรรมอะไรเปลี่ยนและทำไม
- ระบุไฟล์/ระบบที่แตะและส่วนที่ยังเป็นข้อจำกัด
- ระบุการตรวจที่รันจริง พร้อมผล ไม่อ้าง test coverage เกินเส้นทางที่ทดสอบ
- ถ้าเป็นการปรับประสิทธิภาพ แยกผล call count, memory, frame time และ FPS ให้ชัด
- อัปเดตคู่มือหรือ progress ที่เกี่ยวข้องให้ตรงกับโค้ด ไม่เขียนทับบันทึกของผู้อื่นว่าเป็นงานของตัวเอง
- งานที่มีผลเสียร้ายแรง เช่น เซฟเสีย เงินซ้ำ ของหาย หรือ shader ทำให้ชิ้นส่วนหาย ยังไม่ถือว่าเสร็จ

ใช้ [แบบฟอร์มส่งงาน](completion-template.md) เป็นข้อความสรุปสั้น ๆ ตามขนาดงาน ไม่บังคับสร้างไฟล์รายงานใหม่สำหรับทุกการแก้เล็กน้อย

## 11. ตัวอย่างข้อผิดพลาดที่ต้องกันไว้

| สิ่งที่เคยพบ | กฎที่ป้องกัน |
| --- | --- |
| หงอนหายเพราะเกิน vertex attribute limit | ตรวจ shader limits และภาพทุกชิ้น |
| background เรียก 100 ms แต่เก็บ dt แค่ 50 ms | ตรวจเวลาสะสมหลาย cadence |
| dialog สร้างปุ่มใหม่ทุกวินาที | ตรวจ node identity และ focus |
| ค่า alpha จากสูตรต่างจาก Canvas | เทียบผลเดิมก่อนเปลี่ยนการคำนวณ |
| แคชถูก bypass เพราะฟังก์ชันถูก override ทีหลัง | ตรวจ call path ที่ใช้จริง ไม่ดูแค่ชื่อฟังก์ชันแรก |
| CDN ถูกบล็อกจนเทสต์ timeout | รายงานปัญหา environment แยกจากผลทดสอบ |

## 12. เครื่องมือที่มีอยู่

- `node tools/test-followup-performance.mjs` — regression ของ UI, scheduler และคราบตู้แบบแยกส่วนใน Chrome
- `node tools/test-followup-game.mjs` — smoke test ร่วมกับเกมในโปรไฟล์แยก ต้องโหลด Three.js จาก CDN ได้
- `git diff --check` และ `node --check <ไฟล์>` — ตรวจ diff/syntax ไม่ใช่หลักฐานว่าพฤติกรรมถูกต้อง
- [คู่มือศึกษา Two Point Campus](../two-point-campus/index.html) — หลักฐานทางเทคนิคและแนวทดลอง ใช้ประกอบ ไม่ใช่ข้อรับรองว่าเกมเรารองรับคน 1,000 คนแล้ว

เทสต์เก่าอาจอ้าง state หรือ shader รุ่นก่อน ต้องอ่านให้ตรงกับงาน ห้ามเปลี่ยน assertion เพียงเพื่อให้ผ่านโดยไม่ทบทวนพฤติกรรมที่ต้องรักษา
