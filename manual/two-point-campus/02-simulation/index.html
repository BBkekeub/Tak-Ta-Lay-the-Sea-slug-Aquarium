02 — ECS, Burst และงานหลายเธรด

Campus ทำอะไรที่ยืนยันได้

Unity ระบุว่า Campus ใช้ ECS, Burst และ URP สำหรับงานข้ามแพลตฟอร์ม แหล่ง Unity ข้อมูลนี้สอดคล้องกับ assemblies และปลั๊กอินที่พบในเครื่อง

ECS แยกข้อมูลของสิ่งในเกมออกจากระบบที่ประมวลผลข้อมูล ส่วน Burst ใช้คอมไพล์โค้ดที่รองรับให้เป็น native code การจัดข้อมูลต่อเนื่องและลดการวิ่งตามออบเจ็กต์มีโอกาสช่วย CPU แต่ผลเร็วจริงขึ้นกับงานและวิธีเข้าถึงข้อมูล

พบชื่อระบบความต้องการ เช่น ESCharacterModifierFood, Energy, Hygiene และระบบ task แยกประเภท รวมถึง BurstDirectCall ที่เกี่ยวกับการตรวจ attribute และการเคลื่อนที่ หลักฐานระดับนี้ไม่บอกว่าอัปเดตกี่ครั้งต่อวินาทีหรือใช้กี่คอร์

แยกสามเรื่องไม่ให้สับสน

แนวคิดหน้าที่ไม่ได้รับประกัน
ECSจัดข้อมูลและระบบประมวลผลงานจะขนานอัตโนมัติ
Burstคอมไพล์งานที่รองรับให้เหมาะกับ CPUงานทุกชิ้นวิ่งบน worker
Jobsจัดงานและความสัมพันธ์การรองานย่อยมาก ๆ จะเร็วขึ้นเสมอ

Render jobs ที่ประกาศในแพตช์เป็นงานกราฟิก ไม่ใช่หลักฐานว่าความคิดหรือ AI ทุกคนรันพร้อมกันบนคอร์แยก

แนวทางสำหรับเกมเรา

เริ่มจากแยก movement, needs, decision, route request และ rendering แล้ววัดแต่ละกลุ่ม ไม่ต้องย้ายเอนจินหรือเขียน ECS ทั้งเกมทันที

ข้อเสนอเริ่มทดลอง: movement คงที่ 30 Hz พร้อม interpolation, การตัดสินใจทั่วไป 5–10 Hz แบบกระจายคนคนละ tick และความต้องการช้า 1–2 Hz ตัวเลขนี้เป็นค่าทดลองของเรา ไม่ใช่ค่าที่พบใน Campus การซื้อขาย การเข้าคิวและเหตุการณ์สำคัญต้องตอบสนองทันทีเมื่อเกิด event

เก็บเวลาจำลองแยกจากการมองเห็น นอกจอยังซื้อ ขาย รอคิว และหมดเวลาได้ เมื่อแท็บซ่อน browser อาจ throttle timer จึงควรใช้ elapsed time หรือกำหนดวิธีชดเชยอย่างชัดเจน ไม่ถือว่า setInterval รับประกันความถี่

ถ้าจะใช้ Web Worker ให้ส่งข้อมูลแบบชุดและใช้บัฟเฟอร์ที่โอนหรือใช้ซ้ำ แยกงานหาทางที่ไม่ต้องแตะ DOM ก่อน ค่า serialize/ส่งข้อความอาจแพงกว่างานที่ย้าย ต้องวัดก่อนและหลัง

เกณฑ์รับงาน

จำนวน tick ของระบบคิดลดลงโดยเวลาเสนอราคาและผลเกมไม่เปลี่ยน ไม่มีคนข้ามคิวหลังสลับแท็บ และ main-thread p95 ลดลงในฉากเดิม หากค่า worker overhead สูงกว่างานที่ประหยัด ให้ใช้ scheduler บน thread เดิมก่อน
