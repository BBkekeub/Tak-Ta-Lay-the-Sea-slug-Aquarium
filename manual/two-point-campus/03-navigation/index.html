03 — การเดิน การหาทาง และฝูงคน

หลักฐานจาก Campus

พบ ESNavPathPreUpdateSync, ESNavPathUpdate, ESNavPathPostUpdateSync, ESCharacterClusterMovement, NavMeshSourcesCache และ NavMeshRebuildRequestTime ใน metadata ดู รายการชื่อ

ชื่อเหล่านี้สอดคล้องกับการแยกขั้นตอนเส้นทางและโครงสร้าง NavMesh แต่ยังไม่ยืนยันว่าใช้ A*, flow field, hierarchical pathfinding หรือคำนวณทางร่วมกันกี่คน ชื่อ NavMeshAgent ที่มากับ Unity อย่างเดียวก็ไม่พอพิสูจน์ว่าตัวละครทุกตัวใช้ agent นั้น

สิ่งที่พบในเกมเรา

personRoute ใน js/people.js สร้าง nodes จากจุดเริ่ม จุดหมาย พื้นร้าน และมุมสิ่งกีดขวาง จากนั้นเลือก node ระยะน้อยสุดด้วยการสแกนและตรวจ candidate edges ขณะค้นหา มีลูปคู่ตามจำนวน nodes และ personClear ยังตรวจสิ่งกีดขวาง งานจึงโตตามทั้งความซับซ้อนฉากและจำนวนคำขอเส้นทาง ไม่ใช่เฉพาะจำนวนคน

มี spatial grid ใน rebuildPersonGrid และใช้ peopleInArea แล้ว ส่วน route เลี่ยงฝูงคนมี crowdRouteBudget=2 ต่อรอบ step แต่ไม่ได้หมายความว่าคำขอ personRoute ทุกชนิดทั้งเกมถูกจำกัดไว้ 2 คำขอ ต้องตรวจ call sites แยกกัน

ยังพบ PEOPLE.filter ตามด้วย sort เพื่อหาเพื่อนบ้านในเส้นทางเฉพาะบางจุด นี่เป็นจุดควรวัด ไม่ใช่ข้อสรุปว่าเกิด O(N²) ทุกเฟรมเสมอ

ข้อเสนอสำหรับเรา

แคชกราฟพื้นร้านตาม layoutVersion เปลี่ยนเมื่อวาง ย้าย หมุน หรือเก็บสิ่งกีดขวาง การแพน/ซูมไม่ควรสร้างกราฟใหม่ ผูกจุดเริ่มและปลายเข้ากราฟแคชแทนสร้างทุก node ทุกครั้ง

จัดคิวคำขอเส้นทางรวมและให้งบเวลา ไม่ใช่ปล่อยคนทั้งร้านหาใหม่พร้อมกันเมื่อย้ายตู้ ใช้ priority สำหรับคนติดจริง มีอายุคำขอป้องกัน starvation และยกเลิกผลลัพธ์ที่ layoutVersion เก่า

ค้นเพื่อนบ้านจาก spatial grid ก่อน แล้วคัดเฉพาะระยะใกล้ แยก global route ซึ่งเปลี่ยนไม่บ่อยออกจาก local avoidance ที่ตอบสนองเร็ว เส้นทางแคชร่วมใช้ได้เฉพาะรัศมีตัวละครและข้อจำกัดประตูตรงกัน

ทดสอบอะไร

  • ฉากประตูแคบสองทิศทาง: ไม่มีทะลุ ไม่มีติดค้างหรือแย่งคิวไม่สิ้นสุด
  • ย้ายตู้ขวางกลางฝูง: เส้นทางเก่าถูกยกเลิกและทยอยหาใหม่ครบทุกคน
  • กลุ่มครอบครัว: ผู้นำกับผู้ตามไม่แยกจากกันเพราะ scheduler
  • วัดจำนวน route requests, ms ต่อการหาเส้นทาง, อายุคำขอสูงสุด และจำนวนคนติด แทนดู FPS อย่างเดียว

นี่คือแผนพัฒนาจากโค้ดเรา ไม่ใช่อัลกอริทึม Campus ที่ถอดออกมาแล้ว
