ทากทาเล · คู่มือวิจัย Two Point Campusตรวจหลักฐาน 19 กันยายน 2026 · ยังไม่มีผล benchmark 1,000 คน
Two Point Campus เพื่อพัฒนาเกมทากทาเล01 — หลักฐานจากเกมที่ติดตั้ง02 — ECS, Burst และงานหลายเธรด03 — การเดิน การหาทาง และฝูงคน04 — โมเดล กระดูก และแอนิเมชัน05 — การวาดภาพ Culling, LOD และ Batching06 — หน่วยความจำ Pool และเท็กซ์เจอร์07 — เปรียบเทียบและแผนพัฒนาเกมทากทาเล08 — แผนทดสอบคอมสเปคต่ำ09 — แหล่งข้อมูลและสิ่งที่ยังไม่รู้10 — สิ่งที่นำมาปรับได้ นอกเหนือจากลูกค้า11 — ตรวจงานคงเหลือหลังมีการปรับปรุงบางส่วน11 — ทำอะไรไปแล้ว เหลืออะไร

11 — ตรวจงานคงเหลือหลังมีการปรับปรุงบางส่วน

อัปเดตหลังผู้ใช้สั่งแก้

แก้ F1–F4 แล้วในรอบถัดจากรายงานนี้: การ์ดเควส reuse HTML เมื่อข้อมูลเดิม, หน้าสั่งกล่องคงปุ่ม/แถวเดิมและ patch ข้อมูล, เวลา simulation แบ่งก้าวไม่เกิน 50 ms โดยสะสมเวลาที่ค้างไว้ และตู้ไม่มีรอยล้างคำนวณความสะอาดจากค่า alpha โดยไม่สร้าง mask เต็มจนต้องแสดงหรือขัด

ตรวจด้วย node tools/test-followup-performance.mjs ใน Chrome profile แยก: ปุ่ม/focus คงเดิมหลัง 60 calls, การเปลี่ยนเควส/พับ/พัสดุ/เงินทำงาน, elapsed 10 วินาทีได้ simulation 10 วินาที, ก้าวสูงสุด 50 ms และ catch-up จำกัด 20 ก้าวต่อ call โดยไม่ทิ้งเวลาค้าง

ทดสอบระดับคราบ 61 ชุดเทียบ full-mask Canvas ได้ค่าคลาดเคลื่อนสูงสุดประมาณ 1.11e-16; รอยล้างยังใช้ coverage เดิม ค่าการปัด alpha อ่านจาก Canvas 1 pixel แล้วแคชสูงสุด 128 ค่า เพราะ Math.round อย่างเดียวให้ผลต่าง การเข้าสู่หน้าที่แสดงคราบยังสร้าง mask ตามปกติ การหลับเครื่องนานจะทยอยชดเชยเวลา ไม่จำลองทุกอย่างในเฟรมเดียว

เนื้อหา F1–F4 ด้านล่างเป็นหลักฐานก่อนแก้ ส่วน audit-followup.mjs และ followup-audit.json เป็นเครื่องมือ/ผล baseline ของโค้ดก่อนแก้ ไม่ใช่ regression test ของรุ่นปัจจุบัน ยังไม่อ้างผลเพิ่ม FPS บนเครื่องสเปคต่ำ

ทดสอบร่วมกับเกมเต็มผ่าน node tools/test-followup-game.mjs โดยใช้ Chrome profile ชั่วคราวและเซิร์ฟเวอร์พอร์ตสุ่ม ไม่อ่านเซฟผู้เล่น ผล: focus ปุ่มคงเดิมหลัง refresh 60 ครั้ง, ตู้นอกหน้ารายละเอียดไม่สร้าง full mask, หมุนตู้ 4 ด้านมีพื้นผิวคราบครบและค่า dirt คงเดิม, stepPeople รับเวลา 100 ms ครบ 100 ms และไม่มี pageerror/ข้อผิดพลาด shader ที่ตรวจจับได้ การตรวจสี่ด้านเป็น smoke test ของข้อมูล/การเรียกวาด ไม่ใช่ pixel-diff ภาพก่อนหลังทั้งเกม

การรันใน sandbox ครั้งแรกโหลดโมดูล Three.js จาก CDN ไม่ได้ จึง timeout; เมื่อรันด้วยสิทธิ์เครือข่ายที่จำเป็นกับ dependency เดิมของเกมจึงผ่าน ไม่ได้เปลี่ยน import map หรือ dependency ของเกมเพื่อให้เทสต์ผ่าน

ตรวจ working tree วันที่ 19 กันยายน 2026 หลังผู้ใช้แจ้งว่า Claude ทำบางส่วนแล้ว การระบุว่ามีระบบใดอยู่เป็นผลอ่านโค้ดปัจจุบัน ไม่ได้ยืนยันว่าใครเป็นผู้เขียนหรือแก้เมื่อไร รอบนี้แก้เฉพาะคู่มือและเครื่องมือตรวจ ไม่แก้ไฟล์เกมร่วมกับงานที่กำลังทำ

อ่าน บันทึกความคืบหน้าของงานเดิม ร่วมด้วย ซึ่งบันทึกแคชรูปทรงคน/กระจกและผลทดสอบไว้แล้ว ตัวเลขในบันทึกนั้นเป็นผลที่ผู้ทำงานเดิมรายงาน ไม่ใช่ผลที่ทดสอบซ้ำในรอบนี้ รายงานหน้านี้เน้นงานเพิ่มเติมเพื่อไม่ซ้ำส่วนที่จัดการแล้ว

ส่วนที่ไม่ควรเสนอให้ทำซ้ำ

ส่วนสิ่งที่มีอยู่จริง
geometry ตัวบังของตกแต่งfillDepth ขยาย buffer เมื่อความจุไม่พอ ไม่ dispose ทุกเฟรม; updateShopOcclusion อัปเดต furniture เมื่อ layout key เปลี่ยน

หน้าเล่นกับทากframe เช็ก dialog.open/document.hidden และ visibilitychange หยุด/เริ่ม rAF
คราบตู้มีแคชและ next-change time; พื้นผิวสีสร้างเมื่อจำเป็น; ไม่ rebuild คราบทุกเฟรม
การ์ดข้อเสนอpatchTradeCard เปลี่ยน live fields โดยรักษาการ์ดเดิม

ดังนั้นข้อเสนอเดิมเรื่องแคช/หยุดวาดต้องเจาะจุดที่ยังไม่ครอบคลุม ไม่เริ่มทำระบบเดิมใหม่

F1 — การ์ดเควสสร้าง DOM ซ้ำแม้ข้อความเดิม

ตำแหน่ง: js/quests.js, renderCard และ interval ท้ายไฟล์

เมื่อเควสยังไม่สำเร็จ interval เรียก renderCard ทุกวินาที ฟังก์ชันตั้ง card.innerHTML และ bindToggle ใหม่ แม้ชื่อ คำอธิบาย รางวัล และสถานะพับเหมือนเดิม กรณีพับก็ยังเขียน innerHTML ใหม่

ทดสอบฟังก์ชันจริงใน VM ด้วย DOM stub: เรียก 60 ครั้งด้วย state เดิม พบ innerHTML writes 60 ครั้งและ bindToggle 60 ครั้ง นี่เป็นจำนวนคำสั่ง ไม่ใช่เวลาวาดของ browser จึงยังไม่อ้างว่าจะประหยัดกี่ FPS

แนวแก้: เก็บ signature ของเนื้อหาการ์ดและ collapsed state แล้ว patch เมื่อเปลี่ยน แยก updateQuestGlow/การตรวจเงื่อนไขเควสออกจากการสร้างเนื้อหา อย่าหยุดตรวจเควสเพื่อประหยัด UI

ทดสอบรับงาน: state คงเดิม 60 ticks ไม่ rebuild เนื้อหาหลังครั้งแรก; รับรางวัล เปลี่ยนเควสและพับ/ขยายยังถูก; focus ของปุ่มไม่ถูกสร้างทับเอง

F2 — หน้าสั่งกล่องทากสร้างทั้ง dialog ทุกวินาที

ตำแหน่ง: js/slug-box-shop.js, renderSlugShop และ interval 1,000 ms

ขณะ dialog เปิด renderSlugShop สร้างรายการสินค้า พัสดุ ปุ่มทั้งหมดใหม่ผ่าน innerHTML แล้วผูก onclick ใหม่ หน้าที่เปลี่ยนทุกวินาทีจริง ๆ คือ countdown ส่วนสินค้าไม่จำเป็นต้องสร้างใหม่ทั้งหมด เมื่อไม่มีพัสดุก็ยังทำ

ทดสอบฟังก์ชันจริงด้วย state คงที่และรายการว่าง 60 calls พบ 60 innerHTML writes เช่นกัน มีความเสี่ยง focus หลุดเพราะ DOM ปุ่มถูกแทน แต่ยังไม่ได้ทดสอบปฏิสัมพันธ์ browser เพื่อยืนยันอาการ focus ในรอบนี้

แนวแก้: สร้าง shell ครั้งเดียว ใช้ id พัสดุเป็น key อัปเดต countdown/text/disabled และ reconcile เฉพาะรายการที่เข้าออก ตรวจ stock กับเงินต่อได้ตามเดิม

ทดสอบรับงาน: จับปุ่มเดิมไว้แล้วรอหลาย ticks node ยังเดิม; countdown เดิน; ปุ่มซื้อเปลี่ยนตามเงิน; พัสดุถึงแล้วเปิดได้ครั้งเดียว

F3 — คราบตู้ที่ไม่แสดงยังทำ mask raster/readback เมื่อค่าคราบเปลี่ยน

ตำแหน่ง: js/tank-hygiene.js, tankHygiene → rebuildAlgaeSurface และ interval ที่วน G.objs/G.shelter

แคชมีแล้วและข้ามการ rebuild จนถึง next-change แต่เมื่อคราบเปลี่ยน ฟังก์ชันยังสร้าง mask canvas 3 หน้า อ่าน getImageData 192×192 ต่อหน้า แล้วรวมค่า coverage เพื่อใช้คำนวณ dirt แม้ตู้ไม่ได้เปิดดู สิ่งนี้เป็นงานภาพเพื่อได้ค่าจำลอง ไม่ใช่การวาดสีคราบที่ผู้แก้ก่อนหน้าแยก lazy ไว้แล้ว

การอ่านโค้ดยืนยัน 110,592 pixels ต่อหนึ่งการ rebuild ของตู้ ไม่ใช่ต่อเฟรม และไม่ใช่ค่าระยะเวลาที่วัดจริง ตู้หลายใบที่เริ่มเวลาเดียวกันมีโอกาสครบกำหนดพร้อมกัน จึงควรจับ spike ตอนข้ามช่วง 15 นาที/ช่วงเพิ่มคราบก่อนตัดสินความสำคัญ

แนวแก้ที่เสี่ยงต่ำกว่าเขียนใหม่: เพิ่มทางลัดเฉพาะตู้ที่ไม่มีรอยล้าง ใช้ข้อมูลระดับคราบคำนวณค่าเฉลี่ยโดยไม่สร้าง canvas สำหรับ simulation ส่วนกรณีรอยล้างซ้อนต้องรักษาการรวม alpha เดิม หรือมี coverage data แยกที่ให้ผลเทียบเท่า ห้ามเฉลี่ย 144 ช่องแทนทุกกรณีโดยไม่ตรวจผล

ทดสอบรับงาน: ค่าความสะอาด/การผสมพันธุ์ก่อนหลังเท่ากันภายใน tolerance ที่กำหนด โดยระวังการปัด alpha เป็น 8-bit; ทดสอบรอยล้างซ้อนและคราบกลับมา; ภาพสี่มุมไม่เปลี่ยน; วัด mask rebuild/readback ตามจำนวนตู้

F4 — เวลาลูกค้าช้าลงเมื่อหน้าร้านไม่ได้วาด

พบระหว่างตรวจการแยก simulation แม้หัวข้อหลักรอบนี้เป็นระบบอื่นก็ควรบันทึก เพราะเกี่ยวกับ timer/ข้อเสนอทั้งเกม

ตำแหน่ง: js/shop-floor.js, stepShopSimulation ตั้ง interval 100 ms; js/people.js, stepPeople จำกัด dt ไม่เกิน 0.05 วินาที

เมื่ออยู่ในตู้หรือหน้าแข่ง fallback เรียก stepPeople ตาม interval แต่เวลาที่รับได้ต่อครั้งสูงสุด 50 ms การทดสอบ prefix ของ stepPeople ด้วย performance.now เพิ่มครั้งละ 100 ms จำนวน 100 ครั้ง ได้ _peopleT ประมาณ 5 วินาทีจาก elapsed 10 วินาที ภายใต้ cadence นี้วงจรที่ใช้ dt จึงเดินครึ่งหนึ่ง ยังไม่ใช่ผลทดสอบเบราว์เซอร์เต็มฉาก เพราะ browser อาจเรียกช้ากว่านี้ด้วย

แนวแก้: แยกเวลา simulation/timer จาก movement step ถ้าต้องจำกัดก้าวเดินให้ substep ตามงบพร้อมนโยบาย catch-up ที่ชัดเจน หรือใช้ absolute deadline สำหรับ timer อย่าแก้โดยขยาย dt ก้อนเดียวโดยไม่ตรวจการชนและคิว

ทดสอบรับงาน: เวลาข้อเสนอ/การเดินในฉากหน้าและหน้าอื่นสอดคล้องตามนโยบาย; หลังซ่อนแท็บไม่มีการข้ามคิวหรือกระโดดทะลุสิ่งกีดขวาง และไม่มี catch-up ยาวจน UI ค้าง

งานรองที่ยังไม่ยืนยันว่าเป็นคอขวด

  • econ-stats.js อัปเดตข้อความแผง settings ทุกวินาทีแม้แผงปิด แยกการเก็บสถิติกับการเขียน UI ได้ แต่ปริมาณงานน้อยกว่ารายการใหญ่ ต้องวัดก่อน
  • breed-news.js เก็บ snap ตาม id ตู้โดยไม่มีการลบ id ที่หายจากรายการใน scan อาจสะสมเมื่อสร้าง/ลบตู้ต่อเนื่อง ค่าแต่ละรายการเล็ก ยังไม่ใช่หลักฐาน memory leak ขนาดใหญ่
  • คงข้อเสนอเรื่อง autosave/หน้าโหลดจากหมวด 10 ไว้ แต่ยังไม่วัด latency รอบนี้ ไม่กล่าวว่าถูกแก้แล้วหรือหนักที่สุด

หลักฐานและขอบเขต

ผลทดสอบและ hashes เก็บ fingerprints และ anchor lines ของไฟล์ในรอบตรวจ รันซ้ำจากรากโปรเจกต์ด้วย node manual/two-point-campus/tools/audit-followup.mjs หากฟังก์ชันหรือพฤติกรรมเปลี่ยนสคริปต์จะให้กลับมาประเมินใหม่

ไม่มีการเปิดหรือแก้เซฟผู้ใช้ ไม่ได้วัด FPS หรือจำลองการ์ดจอสเปคต่ำ ยังไม่เรียกข้อเสนอเหล่านี้ว่าการแก้เสร็จ ลำดับเหมาะสมคือแก้ความถูกต้อง F4 แล้วเก็บ F1/F2 ที่ขอบเขตเล็ก และวัด F3 ในฉากตู้มากก่อนลงมือเปลี่ยนการคำนวณ
