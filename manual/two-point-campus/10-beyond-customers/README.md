# 10 — สิ่งที่นำมาปรับได้ นอกเหนือจากลูกค้า

มีผลตรวจต่อพร้อมแยกสิ่งที่ทำแล้วและจุดที่ยังเหลือใน [หมวด 11](../11-followup-audit/README.md) โดยเฉพาะ geometry ตัวบังมีการ reuse อยู่แล้ว ไม่ควรตีความว่าต้องสร้างระบบแคชใหม่ทั้งหมด

ตรวจโค้ดวันที่ 19 กันยายน 2026 ข้อเสนอนี้ยังไม่ได้เปลี่ยนระบบเกม ความสำคัญในตารางเป็นลำดับเริ่มวัด ไม่ใช่ผลพิสูจน์ว่าระบบใดหนักที่สุด

## ภาพรวม

| ระบบเรา | สิ่งที่มีแล้ว | สิ่งที่ควรเพิ่มหรือวัด | ลำดับเริ่ม |
| --- | --- | --- | --- |
| ทากจำนวนมาก | แคช แบ่งงานวาด และท่าร่วมบางกรณี | จัดงบตามขนาดบนจอและความสำคัญของการกระทำ | สูง |
| กระจก น้ำ และเอฟเฟกต์ | depth/การบังตามฉาก | วัด overdraw และความละเอียด buffer | สูง |
| ของตกแต่ง | InstancedMesh และแชร์ texture/material | วัดการเปลี่ยน batch, LOD รายชิ้น และอายุแคช | สูง |
| เซฟ | แยกข้อมูลเซฟออกจากแคชภาพ | วัด stringify/sign/write และลดงานซ้ำ | สูง |
| หน้าโหลด | decode รูปและทยอยอบภาพ | โหลดตามสิ่งที่จะใช้ ลดการอบของในคลังก่อนเข้าเกม | กลาง |
| หน้ารายการ/ตลาด | แคชภาพและหยุด loop เมื่อปิด | วาดเฉพาะการ์ดใน viewport อัปเดตเฉพาะข้อมูลเปลี่ยน | กลาง |
| โหมดคุณภาพ | มีค่าจำกัดในหลาย renderer | รวมเป็น preset และทดสอบทั้งเกม | กลาง |

## ทาก — แบ่งงบภาพตามสิ่งที่ผู้เล่นเห็น

js/slug-3d.js มีการใช้ AnimationMixer ต่อ instance, reuse slot, release skeleton และแชร์ pose ตาม state/phase ในเงื่อนไขฝูงเกิน 24 ตัวอยู่แล้ว ใน flush มีการจำกัดรอบวาดและงานที่เลือกมา จึงไม่ควรเพิ่มแคชซ้อนโดยไม่วัด หรือกล่าวว่าเกมยังไม่มีการแชร์ท่า

แนวทางต่อยอด: ทากที่ถูกเลือก ถูกอุ้ม กิน ผสมพันธุ์ หรือแข่งขันต้องได้ความสำคัญสูงกว่าทากที่อยู่ไกลและยืนนิ่ง ทากเล็กบนจอใช้ภาพละเอียดน้อยลงและอัปเดตท่าห่างลงได้ แต่การหิว โต บัฟ และการแข่งต้องเดินตามเวลาเดิม

สิ่งที่ต้องระวังคือ starvation: ตัวไกลต้องไม่ค้างภาพตลอดเพราะตัวใกล้แย่งงบทุกครั้ง ใช้อายุงานประกอบ priority ตรวจว่าการแก้สี ยีน ทิศ เกาะกำแพง หรือการบังทำให้แคช invalid ถูกต้อง

แนวคิดลดรายละเอียดตามขนาดบนจอสอดคล้องกับแนวปรับสิ่งของในแพตช์ Campus แต่ priority ของทากเป็นข้อเสนอของเรา ไม่มีหลักฐานว่าพวกเขาใช้สูตรเดียวกัน

## ตู้ กระจก น้ำ และเอฟเฟกต์ — ลดพิกเซลที่วาดซ้ำ

ตู้จำนวนมากมีพื้นผิวโปร่งใสซ้อนกัน แม้ geometry น้อยก็อาจต้องประมวลผลพิกเซลเดิมหลายรอบ การลดเหลี่ยมอย่างเดียวไม่แก้กรณีนี้ ต้องแยกวัดภาพกระจก เอฟเฟกต์ และทาก

ทดลองปิดประกาย/ฟองที่เล็กจนมองไม่เห็น ลดความละเอียดชั้นเอฟเฟกต์ และรวมชั้นโปร่งใสที่ให้ผลเหมือนกันเฉพาะเมื่อรักษาภาพได้ ลดพื้นที่วาดให้ตรงขอบเขตวัตถุ ตรวจ depth/ลำดับโปร่งใสทุกมุมก่อนรับงาน

หลักฐาน Campus เรื่องลด transparency ของ VFX เป็นทิศทางสนับสนุน แต่ยังไม่ได้อ่าน implementation น้ำหรือกระจกของ Campus ดู [แหล่งข้อมูล](../09-sources/README.md)

## ของตกแต่ง — ใช้ของเดิมร่วมกันและไม่สร้างใหม่ตอนแพน

js/decor-glb.js มี assetCache, materialCache, textureCache และ InstancedMesh รวมถึงการ dispose ของบางส่วนแล้ว นี่เป็นฐานที่ดี สิ่งที่ต้องวัดต่อคือการสร้าง batch ใหม่เมื่อจำนวนของเปลี่ยน การ rebuild geometry ตัวบัง และ memory หลังเปลี่ยนตู้หลายครั้ง

ใช้รุ่นเรียบเมื่อของมีขนาดเล็กบนจอ แคชรูปทรงคงที่ตาม layout/material version และกำหนดเพดาน asset ที่ไม่ใช้งาน การแชร์ material ต้องระวังเปลี่ยนสีชิ้นหนึ่งแล้วไปเปลี่ยนชิ้นอื่นโดยไม่ตั้งใจ

ตรวจจำนวน mesh builds ระหว่างแพน/ซูมควรเป็นศูนย์สำหรับ geometry คงที่ อย่า dispose แล้วสร้างใหม่ต่อเฟรม และอย่าสรุปจากการพบคำว่า dispose ในโค้ดว่ามี churn โดยไม่ตรวจ call frequency

## เซฟ — หลีกเลี่ยงกระตุกเป็นจังหวะ

js/save.js ตั้ง saveGame ทุก 3 วินาที มีการสร้างข้อมูลเซฟ JSON.stringify, CoinGuard.sign และเขียน localStorage ข้อมูลภาพแคชถูกตัดออกอยู่แล้ว แต่กระบวนการ serialize/sign/write ยังเป็น synchronous บน main thread

วัดทั้งสามช่วงกับเซฟเล็กและใหญ่ก่อน ถ้าพบ spike ให้แยกสถานะสำคัญ เช่น ซื้อขาย/เงิน ออกจากข้อมูลที่เปลี่ยนตลอด เช่นตำแหน่ง ใช้ dirty versions และ debounce กับการแก้เป็นชุด พร้อม checkpoint ตามเวลา ตำแหน่งเคลื่อนไหวอาจทำให้ dirty ตลอด จึงใช้ dirty flag ตัวเดียวอาจไม่ช่วย

ถ้าเซฟใหญ่จนจำเป็นค่อยพิจารณา IndexedDB พร้อม transaction และ migration การเปลี่ยน storage ไม่ได้ทำให้ JSON.stringify หรือการสร้าง snapshot หายไปโดยอัตโนมัติ ต้องรักษา CoinGuard, ความสอดคล้องข้อมูล และ load compatibility ห้ามเพิ่มช่วงเสี่ยงข้อมูลสูญโดยไม่กำหนด checkpoint ชัดเจน

เรื่องเซฟนี้เป็นข้อค้นพบในเกมเรา ยังไม่มีหลักฐานว่า Campus ใช้กลยุทธ์เซฟแบบใด

## หน้าโหลด — เข้าเล่นเร็วโดยไม่ย้ายอาการค้างไปหลังโหลด

js/boot.js decode รูปก่อนใช้งานและทยอยอบสไปรต์ โดยรวบทากในร้าน ที่พัก และคลัง allSlugs แล้ว warm-up ทั้งหมด พร้อม yield เมื่อใช้เวลาสะสมเกินประมาณ 24 ms

ข้อเสนอคือแบ่งของจำเป็นต่อฉากแรกกับของที่ยังอยู่คลัง อบฉากแรกให้พร้อมแล้วทยอยเตรียมส่วนอื่นตามงบเวลา การเช็กเวลาเมื่อจบงานหนึ่งชิ้นไม่สามารถป้องกันชิ้นเดียวใช้เวลานานเกินงบ ต้องวัด worst-case ต่อชิ้น และแบ่งย่อยหรือ reuse งานนั้นถ้าจำเป็น

ตรวจว่าเส้นทาง 3D ที่ใช้อยู่ต้องการสไปรต์ใดสำหรับ thumbnail/สำรองจริงก่อนตัด warm-up อย่าลบขั้นตอนแล้วทำให้เปิดคลังครั้งแรกค้างแทน วัด cold load, warm load, เวลาเล่นได้ และ first-open ของแต่ละหน้าแยกกัน

## UI และตลาด — อัปเดตเท่าที่มองเห็นและเปลี่ยนจริง

js/trade.js มี patchTradeCard อัปเดตข้อความและปุ่มเฉพาะที่เปลี่ยนอยู่แล้ว js/world-market.js มีแคชจำกัด 200 รายการและ animation loop เฉพาะตอนตลาดหรือภาพขยายเปิด

ต่อยอดด้วย viewport visibility ของแต่ละการ์ด ภาพนอกส่วนที่เลื่อนเห็นไม่ต้องวาด สถานะราคา/ข้อเสนอใช้ data version เป็นตัว invalidation และอัปเดตตัวเลขเวลาแยกจากภาพทาก จอคอมร้านควรอยู่นิ่งจนมี event ตามกฎ AGENTS.md

เรื่อง UI นี้เป็นข้อเสนอจากโค้ดเรา ไม่ใช่ข้อยืนยันจากระบบ UI ของ Campus

## โหมดประหยัดที่ทำงานทั้งเกม

ตั้ง preset เดียวควบคุม render scale, ความถี่ท่าทางไกล, จำนวนเอฟเฟกต์ และ texture/LOD ที่เหมาะสม แยก setting ภาพจากจำนวนลูกค้าและความเร็วเศรษฐกิจเพื่อไม่ให้คอมอ่อนเสียเปรียบ

หากใช้ adaptive quality ให้ปรับจาก frame-time history พร้อมช่วงรอและ hysteresis อย่าปรับตาม FPS เฟรมเดียวจนภาพคม/เบลอสลับตลอด นี่เป็นข้อเสนอของเรา ยังไม่ยืนยันว่า Campus ใช้ adaptive resolution

## ลำดับทดลองและเกณฑ์ผ่าน

เริ่มจากบันทึกเวลาทั้งเฟรมพร้อม marker ของ save, slug update/render, decor, UI และเอฟเฟกต์ แล้วทดสอบเปิด/ปิดทีละระบบในฉากเดิม เลือกแก้ระบบที่กินเวลาจริงมากที่สุด ไม่เลือกจากชื่อเอนจินหรือจำนวนเหลี่ยม

ทดสอบร้าน 1/10/30 ตู้ จำนวนทากและของตกแต่งที่กำหนดคงที่ แพนสี่มุม เปิด/ปิดตลาด เข้าออกตู้ และปล่อย autosave อย่างน้อยหลายรอบ เปรียบเทียบ p95/p99, ช่วงกระตุก, heap และความถูกต้องของภาพ/เซฟ ก่อนอ้างว่าเร็วขึ้น
